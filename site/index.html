Why this exists

Browser agents see pixels. Bugs live underneath.

Most browser agents take a screenshot, guess, and click. When a button silently fails, they report "it didn't work" and stop. A human engineer would open DevTools. This runtime gives the agent DevTools, organised so it can reason about cause and effect, and hands a person the evidence.

A typical browser agent

  • Sleeps a fixed time and hopes the page finished loading
  • Rereads the whole page after every step to spot a change
  • Sees "nothing happened" when a click throws a silent error
  • Cannot test what happens when the backend fails
  • Loops or times out on a CAPTCHA
  • Leaves a chat transcript, not something a team can use

With Agent Browser Runtime

  • Waits until the DOM is stable and the network is quiet
  • Gets a short diff: "button now disabled", "dialog opened"
  • Asks what a click caused and gets the request, script line and error
  • Breaks one API on purpose and checks the error state
  • Stops, alerts a person, and waits for them to clear it
  • Leaves an HTML report, a Playwright test and a GitHub issue draft

How it works

The agent decides. The runtime handles the browser.

One rule keeps it reliable: the agent chooses what to do next; the runtime owns the browser mechanics (waiting, evidence, safety, cleanup). Playwright performs actions. The Chrome DevTools Protocol watches everything the page does.

Act. The agent calls browser_click by visible name. The runtime starts action N.
Wait. It waits until the DOM stops changing and the network goes quiet.
Watch. CDP records requests, bodies, console calls and exceptions, each tagged with N.
Explain. The agent asks what N caused and gets a tree, or a diff of what changed.
The agent owns decisionsWhere to go, what to click, and whether the test passed.
The runtime owns mechanicsWaiting, evidence, redaction, screenshots, cleanup.
People own the risky partsChallenges and two-factor steps pause for a person.

Playwright + CDP

Why not just Playwright and an agent?

Playwright is excellent at doing things in a browser. But when a test fails, the answer is usually in what the browser saw, not in what the agent clicked. That is what CDP adds.

What is CDP?

The Chrome DevTools Protocol is the channel Chrome's own DevTools uses to talk to the browser. Every time you open the Network or Console tab, DevTools is reading CDP events: each request and who started it, response bodies, console calls with stack traces, uncaught exceptions, frames, and browser warnings.

Playwright is the hands: it finds the button and clicks it reliably. CDP is the flight recorder: it writes down everything the page did afterwards, and why.

This runtime uses both. Playwright acts, CDP observes, and every CDP event is tagged with the action that caused it, so the agent can ask "what did my click do?" and get one answer instead of a pile of logs.

"Playwright + agent" means an agent driving the browser with clicks and snapshots only. Playwright itself can expose some of this data with extra code; this runtime does that work once, bounds it, redacts secrets, and links it to actions.

Capabilities

What an engineer does in DevTools, as tools an agent can call.

Each capability is a normal MCP tool with the same schema in Claude Code and the Agent SDK.

What did this click cause?

A cause-and-effect tree per action: the requests it started, the script line and function behind each, and the errors that followed, even across timers and promises.

browser_explain_action

What changed on the page?

removed checkbox "A checkbox"
changed textbox "Note": now enabled
added dialog "Sign in"

Diffs of the accessibility tree instead of rereading the whole page; under 5% of a full snapshot in our tests.

browser_changes

Break it on purpose

Make one API return 500, fail, slow down or return rewritten JSON, inside this browser only. Evidence labels every injected response, so "we broke it" never looks like "the server broke".

browser_fault · browser_faults_clear

A report people can read

report.html in every run folder: the goal, findings by severity, first-party bugs separate from ad noise, a copy-ready GitHub issue, the full action timeline and screenshots.

browser_report

From exploration to regression test

Export the session as a Playwright .spec.ts. Verified checks become expect() assertions, passwords never leave, and a HAR replays recorded API responses.

browser_export_test

Knows when to stop

Detects reCAPTCHA, hCaptcha, Turnstile, Cloudflare challenges and two-factor prompts. It never solves them: it alerts a person (MCP, desktop, Slack or Teams webhook) and waits for them in the visible browser.

browser_request_handoff

Verified actions

Checks that wait for an expected URL, text, value or element state with a deadline, and short sequences that stop at the first failure with partial evidence.

browser_verify · browser_sequence

Secrets stay secret

The runtime signs in with configured accounts so the model never sees a password. Tokens, cookies and credentials are redacted from snapshots, evidence, reports and exports.

browser_login · redaction everywhere

Escape hatch for experts

Any DevTools command or event (performance metrics, coverage, audits) behind a flag. Calls are recorded and redacted; commands that close or crash the browser stay blocked.

browser_cdp · BROWSER_RAW_CDP=1

How it can be used

From one prompt to a team workflow.

Give the agent a URL and a goal. It explores on its own and returns evidence, not guesses.

Exploratory QA"Log in, add two items, check out." Every bug comes with the click, the request and the script line.
Root-cause debugging"Why is the cart empty?" The agent reproduces it and shows the chain from click to failing response.
Error-state testingBreak the search API and check that the user sees an error, not "no results".
Pull request previewsWalk the changed flow on a preview URL and pass only when every verified check matched.
Regression tests for freeTurn one good exploratory run into a Playwright spec you keep in CI.
Unattended runs that page a personNightly agents post to Slack when a CAPTCHA or 2FA prompt needs a human.
Your own agent productsEmbed it in-process with the Claude Agent SDK. Your orchestrator owns the session and can salvage evidence after a timeout.
Bug reports developers act onHand over report.html and a GitHub issue draft with steps, expected, actual and evidence.

Get started

Two minutes to a browser-capable Claude.

1 · Install

Chromium downloads into the package, so there is no separate browser setup.

git clone https://github.com/amankulkarni29/agent-browser-runtime.git
cd agent-browser-runtime
pnpm install && pnpm build

2 · Connect Claude Code

Headed mode lets you watch, and step in when a challenge appears.

claude mcp add agent-browser -e HEADED=1 \
  -- node "$(pwd)/dist/adapters/mcp-server.js"

3 · Ask for a QA pass

Type a short request, or start with this one.

Use agent-browser to test https://www.saucedemo.com
as problem_user / secret_sauce. Report every bug
with evidence, then call browser_report.
